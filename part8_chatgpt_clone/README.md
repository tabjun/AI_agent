## 1. 비동기(Async/Await) 호출의 판단 기준

### 왜 어떤 코드에는 `await`를 붙이고, 어떤 곳엔 `asyncio.run()`을 쓰는가?
그 차이는 **"누가 이 함수를 호출하느냐"**와 **"함수의 정의가 어떠한가"**에 달려 있다.

*   **판단 근거 (함수 시그니처):** 함수가 `async def`로 선언되어 있다면, 이 함수는 호출 즉시 결과를 주는 것이 아니라 "나중에 실행될 약속(코루틴)"을 반환한다. 이 약속을 실행해서 결과값을 꺼내려면 반드시 `await` 키워드가 필요하다.
*   **비동기 환경 여부:**
    *   **비동기 함수 내부:** 다른 비동기 함수를 호출할 때는 `await`를 직접 사용할 수 있다. (예: `await session.get_items()`)
    *   **동기 환경 (Streamlit 메인 루프):** Streamlit의 일반적인 스크립트 실행 환경은 동기(Sync) 방식이다. 동기 환경에서는 `await`를 직접 쓸 수 없으므로, **`asyncio.run()`**이라는 도구를 사용하여 비동기 함수를 강제로 실행시켜야 한다.
*   **주의할 점:** `asyncio.run(await ...)`와 같이 중복으로 사용하는 것은 문법적 오류이다. `asyncio.run()` 안에는 실행할 코루틴(함수 호출 형태)만 전달해야 한다.

## 2. Streamlit 채팅 레이아웃: "상자(Container) 안에 상자" 개념

채팅 구현 시 `run_agent()`의 위치를 선정하는 것은 레이아웃의 성패를 결정한다. 이를 이해하기 위해 **"상자(Box) 비유"**를 활용한다.

### 📦 직관적인 비유: 상자 개념
Streamlit에서 `with st.chat_message('human'):` 코드는 화면에 **'사용자용 전용 상자'**를 하나 만드는 것과 같다. 이 `with` 문 안에 들어가는 모든 내용(`st.write` 등)은 그 상자 안에 차곡차곡 쌓이게 된다.

### ❌ 문제 상황: 상자 안에 상자 넣기 (Nesting Error)
```python
if prompt:
    with st.chat_message('human'):
        st.write(prompt)
        # ⚠️ 사용자 상자가 아직 열려있는 상태에서...
        asyncio.run(run_agent(prompt)) # 이 함수 내부에서 'AI용 상자'를 또 만들려고 함!
```
*   **문제의 핵심:** `run_agent()` 함수 내부에는 `with st.chat_message('ai'):` 코드가 들어있다. 위와 같이 작성하면 **사용자 상자 안에 AI 상자를 집어넣으려는 시도**가 된다.
*   **결과:** Streamlit은 디자인 규칙상 **채팅 상자 안에 또 다른 채팅 상자를 넣는 중첩(Nesting)을 허용하지 않는다.** 이로 인해 레이아웃이 깨지거나 출력이 비정상적으로 발생한다.

### ✅ 해결책: 독립적인 상자 배치
사용자가 질문을 입력했을 때만 실행되어야 하므로 `if prompt:` 안에는 있어야 하지만, 상자가 겹치면 안 되기 때문에 사용자 상자(`with`)는 완전히 닫은 후 AI 상자를 열어야 한다.

```python
if prompt: # 1. [실행 조건] 사용자가 입력을 했을 때만 실행해라!
    
    with st.chat_message('human'): # 2. [사용자 상자 열기]
        st.write(prompt)           # 3. 사용자가 쓴 글을 상자 안에 넣는다.
    # 4. <여기서 사용자 상자가 완전히 닫힘 - 들여쓰기 끝>

    asyncio.run(run_agent(prompt)) # 5. [AI 상자 생성] 이제 독립적으로 AI 상자를 만들어 답변을 써라!
```

## 3. 핵심 요약 및 복습 포인트

1.  **`if prompt:` 안에 넣는 이유:** 사용자가 아무런 입력을 하지 않았는데 AI가 먼저 답변을 생성하는 불필요한 실행을 막기 위해서이다. (실행 조건의 제어)
2.  **`with` 블록 밖에 넣는 이유:** 사용자 말풍선 안에 AI 말풍선이 들어가는 "레이아웃 인셉션" 상황을 방지하고, 대등한 위치에 메시지를 쌓기 위해서이다. (레이아웃의 독립성)
3.  **개발 시 팁:** Streamlit에서 `with`는 시각적인 경계를 만드는 작업이다. 내가 지금 만드는 UI 요소가 다른 요소의 **내부**에 들어가야 하는지, 아니면 **다음**에 와야 하는지를 들여쓰기(Indentation)를 통해 명확히 구분해야 한다.

# 2026.4.21 공부: 데이터 구조 안정성 및 비동기 초기화

오늘의 학습은 OpenAI Assistants API의 복잡한 데이터 구조를 안전하게 처리하는 방법과 Streamlit의 실행 생명주기 내에서 비동기 함수를 초기화하는 이유를 다룬다.

### 1) `st.write` 대신 `st.markdown`을 사용하는 이유
*   **명시적 렌더링:** `st.write`는 입력 타입에 따라 출력을 자동으로 결정하는 범용 함수다. 반면, 챗봇 응답은 **코드 블록, 굵은 글씨, 리스트** 등 마크다운 형식이 핵심이다.
*   **일관성:** `st.markdown`을 사용하면 Streamlit이 해당 텍스트를 마크다운으로 해석하도록 강제하므로, 텍스트의 형식이 깨지지 않고 의도한 대로 렌더링됨을 보장할 수 있다.

### 2) 복잡한 `isinstance` 및 `len()` 체크가 필요한 이유
OpenAI의 최신 SDK(특히 Assistants API)는 메시지 내용을 단순 문자열이 아닌 **리스트 형태**로 반환하는 경우가 많다.
*   **구조 대응:** `content=[{ "type": "text", "text": { "value": "..." } }]`와 같은 구조에서 실제 텍스트만 뽑아내기 위해 `isinstance(message['content'], list)` 체크가 필요하다.
*   **방어적 프로그래밍:** `len(message['content']) > 0` 체크는 리스트가 비어있을 때 `[0]` 인덱스에 접근하여 발생하는 **`IndexError`를 방지**하는 최소한의 안전장치다. 
*   **앱 안정성:** Streamlit은 코드 한 줄에서 에러가 나면 전체 앱 화면이 멈춘다. 유저에게 JSON 객체를 그대로 노출하지 않고, 어떤 상황에서도 앱이 죽지 않게 하기 위해 다소 보수적인 타입 체크를 수행하는 것이 실무적인 정석이다.

### 3) `asyncio.run(display_chat_history())`의 역할
*   **상태 복원 (Load History):** 이 코드는 앱이 새로고침(Rerun)될 때마다 데이터베이스(SQLite)에 저장된 이전 대화 내용을 읽어와 화면에 다시 그려주는 역할을 한다.
*   **동기-비동기 브릿지:** `display_chat_history`는 DB 조회를 위해 `async def`로 정의된 비동기 함수다. 하지만 Streamlit의 메인 실행 흐름은 동기 방식이므로, 앱이 시작될 때 이 비동기 작업을 완료하기 위해 `asyncio.run()`으로 감싸서 호출해야 한다.
*   **실행 위치의 중요성:** 채팅 입력창(`st.chat_input`)보다 위에서 실행되어야 이전에 나눴던 대화들이 먼저 화면에 출력되고, 그 아래에 새로운 입력창이 나타나 자연스러운 채팅 흐름을 유지할 수 있다.

# 2026.4.22 학습 내용: Hosted Tools 활용 및 비동기 흐름 이해

### 1. 핵심 개념: Hosted Tools (내장 도구)
기존의 `function calling`은 개발자가 직접 함수를 정의하고 실행 로직을 작성해야 했습니다. 반면, **OpenAI Agent SDK의 Hosted Tools**는 OpenAI 인프라에서 직접 실행되는 도구(예: `WebSearchTool`)를 모델에 간단히 연결만 하면 바로 사용 가능한 방식입니다.

### 2. 'role' Key Error가 발생하는 이유 및 해결
`WebSearchTool`을 사용하면 세션(DB)에 사용자/AI 메시지 외에 도구 호출(`tool_calls`) 및 결과 데이터가 섞여 들어옵니다. 이 데이터들은 `role` 키가 없기 때문에, UI 출력 시 `if 'role' in message:`와 같은 방어적 코드가 반드시 필요합니다.

*   **Streamlit 환경 변수:** `STREAMLIT_SERVER_RUN_ON_SAVE=true`를 설정하여 코드가 저장될 때마다 Streamlit이 이를 감지하고 자동으로 화면을 새로고침하게 만든다.

*   **Base64 인코딩:** `file_uploader`로 받은 이미지 파일을 LLM이 인식할 수 있는 텍스트 형태(Base64)로 변환하여 전달한다.
*   **Content List 구조:** OpenAI Agents SDK는 텍스트와 이미지를 동시에 보낼 때 `[{"type": "text", ...}, {"type": "image_url", ...}]` 형태의 멀티모달 리스트 구조를 요구한다.

### 3) Cloudflare Tunnel을 이용한 무료 외부 노출
*   **ngrok과의 차이:** `ngrok` 무료 버전은 인증 및 유효 기간 제약이 있으나, `cloudflared`는 로그인 없이도 안정적인 무료 터널링을 제공한다.
*   **실행 명령어:** `cloudflared tunnel --url http://localhost:8000` 한 줄로 전 세계 어디서든 접속 가능한 보안 터널을 생성할 수 있다.

# 2026.04.23 학습 내용: File Search Tool 활용 및 데이터 관리

OpenAI 플랫폼의 Storage와 Vector Store를 활용하여 대규모 문서를 기반으로 답변하는 `filesearch` 도구의 설정 및 운영 프로세스를 학습한다.

### 1) OpenAI Storage 파일 업로드
*   **파일 관리:** [OpenAI Storage](https://platform.openai.com/storage)는 모델이 참조할 수 있는 데이터 파일을 저장하는 공간이다.
*   **활용:** 우리가 구현한 UI에서 파일을 읽어 답변에 활용하려면, 먼저 이 스토리지 영역에 필요한 문서(PDF, 텍스트 등)가 업로드되어 있어야 한다.

### 2) Vector Store 생성의 필수성
*   **검색의 선결 조건:** 파일을 단순히 업로드하는 것만으로는 `filesearch` 기능을 사용할 수 없다. 업로드된 파일들을 효율적으로 검색하기 위해 반드시 **Vector Store(벡터 스토어)**를 먼저 생성해야 한다.
*   **연결 구조:** 생성된 Vector Store에 업로드한 파일들을 연결(Attach)하면, 모델이 질문에 관련된 내용을 수 초 내에 찾아내어 답변의 근거로 활용하게 된다.

### 3) filesearch Tool 설정
*   **도구 활성화:** 에이전트 설정 시 `filesearch` 도구를 명시적으로 추가해야 하며, 이때 앞서 준비한 Vector Store ID를 연동하여 지식 기반 검색이 가능하도록 구성한다.

### 4) 복합 입력(텍스트 + 파일)의 효율적 처리 로직
`st.chat_input(accept_file=True)`를 사용할 때 데이터의 완결성을 높이기 위해 다음과 같은 설계를 적용했다.
*   **역할 분리 (파일 인식 vs 답변 생성):** 
    - 사용자가 파일과 메시지를 동시에 보내면, 먼저 루프를 통해 파일을 OpenAI 서버에 업로드하고 벡터 스토어에 연결하는 **'사전 준비'**를 마친다.
    - 이후 `if prompt.text:` 블록을 통해 사용자의 실제 질문이 있을 때만 에이전트를 가동한다. 이는 파일만 전송했을 때 불필요하게 AI가 답변을 시작하는 것을 방지한다.
*   **멀티모달 입력 우선순위(`image_to_use`):** 
    - 이미지를 업로드할 수 있는 경로가 사이드바(`uploaded_file`)와 채팅창(`chat_image`) 두 곳일 때, 사이드바에 고정된 이미지를 우선적으로 참조하도록 로직을 구성하여 일관된 답변을 유도한다.
*   **객체 참조 최적화:** `prompt` 객체 자체를 출력하는 대신 `prompt.text`를 명시적으로 참조하여, UI에 객체 정보가 아닌 실제 텍스트 메시지만 깔끔하게 표시되도록 구현했다.

# 2026.4.24 multi modal agent 기본 구축 \ 이미지 처리를 위한 base64 처리

멀티모달 에이전트 구현 시 Streamlit의 `st.file_uploader`를 통해 업로드된 이미지 파일을 처리하는 과정에서 `file` 객체와 `file.getvalue()`의 차이점을 이해하는 것이 중요하다.

### 1) `chat_image = file` (UploadedFile 객체 참조)
*   **특징:** Streamlit에서 제공하는 `UploadedFile` 클래스의 인스턴스이다.
*   **구성:** 파일 이름, 타입, 크기 등 메타데이터와 데이터를 읽을 수 있는 메서드를 포함한 '파일 핸들러' 역할을 한다.
*   **한계:** `base64.b64encode()`와 같은 함수는 순수 바이트(bytes) 데이터를 요구하므로, 객체 자체를 넘기면 타입 오류가 발생할 수 있다.

### 2) `file_bytes = file.getvalue()` (바이트 데이터 추출)
*   **특징:** 파일 내부의 실제 이진 데이터(Binary Data)만 뽑아낸 상태이다.
*   **데이터 타입:** `bytes` 타입이다.
*   **활용:** `base64.b64encode(file_bytes)`와 같이 즉시 인코딩이 가능하여, 이미지 분석 전처리를 위한 전송용 데이터 생성에 필수적이다.

### 3) `file = (file.name, file.getvalue())` (튜플 구조 활용)
*   강의와 실습에서 사용하는 이 방식은 파일의 **이름**과 **실제 데이터**를 하나의 패키지로 묶어 관리하기 위함이다.
*   에이전트에게 파일의 확장자 정보를 제공하거나, 나중에 UI에 파일명을 표시할 때 유용하게 활용된다.

### 요약
이미지 분석 전처리를 위해 Base64로 변환할 때는 객체 전체(`file`)가 아닌, `getvalue()`를 통해 추출된 **'순수 알맹이 데이터(bytes)'**를 사용해야 한다.

# 2026.4.24 멀티모달 처리를 위한 세션(Session) 관리 및 이해

멀티모달 에이전트 구현 시, 이미지를 업로드하고 분석을 요청할 때 데이터를 '세션'에 추가하는 과정이 포함됩니다. 이에 대한 개념과 필요성을 정리합니다.

### 1) 세션(Session)이란?
*   **정의:** 사용자가 웹 애플리케이션에 접속해 있는 동안 유지되는 **'일시적인 기억 장치'**입니다.
*   **역할:** 웹은 본래 상태를 저장하지 않는(Stateless) 특성이 있지만, 세션을 통해 "나와 이 사용자 사이에 어떤 대화가 오갔는지"를 기억할 수 있습니다.

### 2) 왜 세션에 저장해야 하는가? (Streamlit의 특성)
*   **코드 재실행:** Streamlit은 버튼 클릭이나 텍스트 입력 등 사용자의 모든 상호작용마다 코드 전체를 위에서 아래로 **다시 실행(Rerun)**합니다.
*   **휘발성 방지:** 세션에 데이터를 명시적으로 저장(`st.session_state` 또는 DB 연동 세션 객체 활용)하지 않으면, 이미지를 업로드한 직후 질문을 입력하는 순간 방금 올린 이미지 데이터는 메모리에서 사라지게 됩니다. 
*   **맥락 유지:** 이전 대화 내용과 이미지를 세션(DB)에 박제해두어야만, AI가 과거의 맥락을 파악하여 연속성 있는 답변을 줄 수 있습니다.

### 3) 세션에 추가하는 코드 분석
```python
# 이미지 데이터를 세션(DB)에 추가하여 저장하는 로직
session.add_items([
    {
        'role': 'user',
        'content': [
            {
                "type": "image_url",
                "detail": "auto",
                "image_url": {"url": data_uri} # base64로 인코딩된 이미지 URI
            }
        ]
    }
])
```
*   **역할:** 사용자가 올린 이미지를 단순히 화면에 보여주는 데 그치지 않고, 에이전트가 참조할 수 있는 **'공식 대화 기록'**으로 편입시키는 과정입니다.
*   **구조:** OpenAI의 멀티모달 규격에 맞춰 `image_url` 타입을 지정하여 세션 객체에 전달합니다.

### 요약
세션은 **"사용자와의 대화 흐름을 잃지 않기 위한 기억 장소"**이며, 여기에 데이터를 추가하는 행위는 **"다음에 올 질문에 대해서도 이 데이터를 잊지 말고 참고하라"**고 기록하는 것과 같습니다.

## 🛠️ Troubleshooting: 400 Errors & SDK Message Schema

프로젝트 진행 중 발생했던 `400 BadRequestError`의 주요 원인과 해결 방법입니다. 이는 OpenAI Agents SDK의 독특한 입력 스펙을 준수하지 않아 발생한 문제입니다.

### 1. Runner.run_streamed 입력 형식 오류 (invalid_type)
- **현상**: `payload = {"type": "message", "role": "user", "content": [...]}` 처럼 dict 전체를 전달할 때 발생.
- **원인**: SDK가 내부적으로 이 dict 전체를 문자열로 취급하여 API에 전달하게 되고, API는 이를 잘못된 형식의 string으로 인식합니다.
- **해결**: 에이전트에게는 순수 텍스트(string) 혹은 `content` 리스트(`[...]`)만 전달하거나, 세션에 먼저 데이터를 추가하는 방식을 사용해야 합니다.

### 2. image_url 데이터 구조 불일치
- **현상**: 일반 OpenAI API 규격인 `{"image_url": {"url": "data:..."}}` 사용 시 발생.
- **원인**: SDK는 `image_url` 키의 값으로 중첩 dict가 아닌 **직접적인 URI 문자열**을 기대합니다.
- **해결**: SDK 전용 규격인 `{"type": "input_image", "image_url": "data:..."}` 형식을 사용해야 합니다.

### 3. 세션 저장 방식의 차이 (Param vs Session)
- **현상**: 이미지를 함수 파라미터로만 넘기고 세션에 저장하지 않을 때 히스토리 참조 불가.
- **원인**: 에이전트가 이전 대화 맥락을 파악하려면 데이터가 `session.add_items()`를 통해 세션 DB에 먼저 박제되어야 합니다.
- **해결**: 이미지를 먼저 세션에 저장한 뒤 에이전트를 실행하면, Runner가 세션에서 자동으로 이미지 데이터를 포함하여 API를 호출합니다.

**한 줄 요약**: SDK에 dict 전체를 넘기면 string으로 인식되어 400, `image_url`이 중첩 dict면 형식 불일치로 400 에러가 발생합니다.
